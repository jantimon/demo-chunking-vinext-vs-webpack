webpack × Rolldown · Next.js Pages Router

Same code,
ten times the files

webpack copies small shared code into every chunk that needs it. Rolldown never copies, so it cuts one chunk for every unique set of importers, and a large app ends up with hundreds of tiny files.

01Why bundlers split code

A page needs its own code plus code it shares with other pages. Put everything in one file and every page download repeats the shared part. Put every module in its own file and the browser makes a request for each of them. Bundlers pick a middle: one file per page, plus chunks for code several pages share.

A module that several pages share, but not all, needs a home. webpack copies it into each page's file when it is under 20 KB. Rolldown never copies: it puts the module into a chunk for exactly that set of pages.

The two differ only on small code that several pages share:

  • webpack copies it. Price, translate, IconButton and useCart sit a second time in the cart page's file.
  • Rolldown gives it a file. One for Price, one for translate, one for IconButton and useCart, and one for Button and styled, because Rolldown doesn't know _app always loads before a page.

React, the 30 KB gallery and code that only one page uses end up the same in both. The product page loads 8 more files with Rolldown: those four, plus one stylesheet each for Button, Price, IconButton and the carousel chunk.

05Who gets the connection first

Chrome tells the server how urgent each file is. Render-blocking CSS is Highest. webpack's scripts load with defer and are Low. vinext's are module scripts and are High from the start. The product image starts at Medium and becomes High only once layout shows it on screen.

Real app · Next.js Pages Router, 225 pages

Both ask for the product image at 0.15 s. webpack has it at 0.77 s. On vinext it shares the connection with about 700 other requests that started at the same moment, and arrives at 1.71 s. The largest paint follows the image within 25 ms in both.

Chrome's "tight mode", which holds back requests early in a page load, is probably not the reason, as it only delays requests below High priority, and only until the HTML reaches <body> (Chromium's scheduler source). A server that sends by priority would put vinext's High scripts ahead of the image while it is still Medium.

06What makes fixing so hard?

  1. 1 · "HTTP/2 makes small files free"

    It removes the six-connection limit, not the cost per file. Each file still pays its own gzip start, its own compile step, and for CSS a render-blocking request. The HTML of the product page carries 1,152 script and preload tags.

  2. 2 · "Port vinext's App Router grouping to the Pages Router"

    vinext already groups chunks the Next.js way, but only for the App Router. We ported its rule: modules that the same set of pages load at start share one chunk.

    ✓

    Start-up code merges. The chunks _app loads go from 136 to 11.

    ✗

    Lazy code stays split. The rule leaves dynamic import() alone, and lazy dialogs reach most of the app: about 500 tiny chunks remain, and the product page still loads about 470 scripts.

    !

    Keep page files out of the groups. vinext's server finds a page's scripts and CSS through the page file's own chunk. Our first port grouped the page files too, and the product page painted without its CSS.

  3. 3 · Manual chunk groups

    Rolldown's codeSplitting.groups with framework, library and app groups cut the files to 371. Each group carries code for other pages too: 3 MB of JavaScript, and the product image appears after 3.6 s instead of 0.85 s.

  4. 4 · Copy small chunks, like webpack

    Rolldown 1.2 can copy small automatic chunks into the chunks that use them: experimentalInlineCommonChunks: { maxSize: 20000 }, webpack's floor. The build drops from 1,618 to 457 files, the product page loads 72 scripts and 33 stylesheets. But copied modules bring their CSS twice, the cascade order changes, and the header logo rendered twice.
